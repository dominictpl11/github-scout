# GitHub Scout — 报告输出格式

本文件定义开发者画像报告的结构与填写规则，**平台无关**。

各 adapter 可以调整呈现细节（表格样式、强调方式），但**章节结构与必填字段不得改动**——这是跨平台结论一致性的一部分。

配套文件：`methodology.md`（流程）、`repo-ranking.md`（评分）。

## 二、字段填写规则

### 2.1 必填与选填

| 章节 | 必填 | 选填 |
|---|---|---|
| 基本信息 | 用户名、加入时间、公开仓库数 | 显示名、简介、followers |
| 技术方向 | 主要语言、主要领域 | 近期方向 |
| 代表项目 | 项目名、用途、技术栈、复杂度 | 代码规模、活跃情况 |
| GitHub 活跃度 | 最近活动、原创/fork 比例 | commit 分布、长期维护数 |
| 综合评价 | 主要方向、技术特征 | 值得关注的项目 |
| 数据说明 | 全部缺口（无缺口则写「无」） | — |

选填字段无数据时**删除该行**，不要留空或填「未知」——留空的表格行会让读者误以为数据获取失败。

### 2.2 主要语言

按仓库数量与代码规模**加权**，而非仅按仓库数。

一个 3 万行的 Rust 项目比十个各 200 行的 Python 脚本更能说明技术方向。附上占比，让读者自行判断权重是否合理。

### 2.3 主要领域

每个领域需要 **≥2 个项目**佐证。单个项目只能说明「做过」，不足以确立方向。

领域用具体表述：写「LLM Agent 框架」而非「AI」，写「React 前端应用」而非「Web」。

### 2.4 复杂度

星级对照见 `repo-ranking.md` 第五节。**同时给出得分**，让评级可追溯——只有星级时，读者无法判断 ★★★☆☆ 是 40 分还是 59 分。

**不得声称排序绝对精确。** 架构复杂度与技术栈难度两项（共 20 分）只对最终 Top N 计算，因此第 N+1 名理论上仍可能反超。报告中提到排序时用「按本次评分」这类措辞，不要写成客观定论。

### 2.5 技术特征

描述可观察的特征，例如：

- 偏工程实现 / 偏算法实验 / 偏工具建设 / 多为学习实践
- 项目集中在少数几个大项目 / 分散在大量小项目
- 长期维护单一项目 / 频繁开新坑
- 独立开发为主 / 参与他人项目为主

**不写**「技术水平较高」「基础扎实」「能力一般」这类评价性表述。报告的职责是呈现事实，判断留给读者。

### 2.6 数据说明

这一节对应可回溯性要求，是报告可信度的基础。

必须列出的情况：

- commit 作者信息不足，个人贡献占比为估算
- 无 README，项目用途为从结构推断
- 仓库数超限，仅对前 N 个做了粗筛
- 教程识别的 README 检查只覆盖了前 15 个候选，其余仅按元数据判定
- commit 总数由贡献者 commit 数求和得出，是近似值
- 某个仓库无法访问
- 在无 API 凭证的降级模式下运行
- 任何标注为「推测」的结论

无缺口时明确写「无」，而不是删除整节——读者需要知道这一节被认真检查过。

---

## 三、事实与推测的区分

报告中的每条结论分两类，**表述方式必须不同**：

| 类型 | 表述 | 示例 |
|---|---|---|
| 观察到的事实 | 直接陈述 | 「该项目有 240 次 commit，跨度 14 个月」 |
| 据此的推测 | 显式标注 | 「从依赖推测该项目用于数据管道（无 README，未经证实）」 |

不允许把推测写成事实。当依据不足时，宁可写「无法判断」，也不要给一个听起来合理的猜测。

---

## 四、空结果与边界情况的报告

以下情况**必须产出报告**，不允许以「无可分析内容」结束。

| 情况 | 报告要点 |
|---|---|
| 公开仓库数为 0 | 说明无公开仓库，无法形成技术画像；若 profile 有简介或站点，指出这是仅有的公开线索 |
| 全部为 fork | 说明公开活动以参与他人项目为主；逐个检查 fork 中是否有实质自有改动，有则作为贡献证据列出 |
| 全部为教程 / 模板 | 说明公开仓库以学习实践为主；按时间线描述学习方向的变化，**不引申为能力判断** |
| 仓库存在但全部为空 | 说明账号已注册仓库但无实质内容 |
| 候选项目不足 N 个 | 有多少列多少，在「数据说明」中说明实际数量 |

这些报告同样要完整填写所有必填字段。仓库数为 0 时，「技术方向」一节写明无法判断的原因，而不是省略该节。

---

## 五、语气要求

- **中立**：呈现事实，不褒不贬
- **克制**：不用「优秀」「出色」「令人印象深刻」这类修饰
- **具体**：用数据代替形容词——写「commit 跨度 14 个月」而非「维护时间较长」
- **不臆测动机**：描述做了什么，不猜测为什么做

报告可能被用于招聘初筛等有实际影响的场景。任何超出公开数据支持范围的评价，都可能对被调查者造成不公平的影响。
