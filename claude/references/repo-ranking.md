# GitHub Scout — 仓库过滤与评分规则

本文件定义仓库的过滤规则与评分模型，**平台无关**。

这是保证跨平台结论一致的关键文件：任何 adapter 对同一个用户的 Top N 排序与复杂度评级都应当由本文件唯一决定。**规则有歧义时，在这里修正，不要在 adapter 里打补丁。**

配套文件：`methodology.md`（流程）、`report-format.md`（输出）。

---

## 一、过滤规则

### 1.1 分类

| 类别 | 判定 | 处理 |
|---|---|---|
| 原创项目 | 非 fork，有实质内容 | 正常评分 |
| fork 项目 | 标记为 fork | 评分后应用降权系数 |
| 教程 / 模板 | 命中 1.2 的信号 ≥2 条 | 评分后应用降权系数 |
| 空仓库 | 无内容或仅有 README/LICENSE | 评分后应用降权系数 |

**降权而非排除。** 所有仓库都参与排序。当一个用户的仓库全是 fork 或全是教程项目时，报告仍需给出有依据的结论。

### 1.2 教程 / 模板项目识别

命中 **≥2 条**即判定：

- **命名信号**：仓库名或描述（**两者都要查**）含以下任一词：`tutorial`、`learn`、`learning`、`practice`、`demo`、`test`、`example`、`sample`、`boilerplate`、`starter`、`template`、`scaffold`、`playground`、`sandbox`、`exercise`、`hello`、`homework`、`assignment`、`course`、`bootcamp`、`训练营`、`课程设计`、`大作业`
- **README 信号**：README 明显是课程模板或脚手架自带，未做实质修改；或内容为教程步骤而非项目说明；或自述为「示例」「练手」「学习时写的」
- **commit 信号**：commit 全部集中在 1～3 天内，且 message 多为 `update`、`commit`、`init`、`fix`、`.` 等无信息量内容
- **结构信号**：目录结构与知名脚手架或教程仓库完全一致，无自有扩展
- **来源信号**：仓库由 template 生成，且生成后改动很少

### 执行方式：逐条计数，不做整体判断

这一步**必须机械执行**，不能凭对仓库的整体印象判断：

1. 对进入粗筛前 15 名的每个候选，**逐词**核对命名信号——把仓库名与描述拼接后小写化，逐个词做子串匹配，**记下命中的词**
2. 无论命名信号是否命中，**都要读这 15 个候选的 README**，核对 README 信号与结构信号
3. 记录每个候选的命中条数，**≥2 条**才判定
4. 在报告的「数据说明」里列出被判定为教程/模板的仓库及其**具体命中的信号**，供读者复核

**不要因为「看起来都是正经项目」就跳过 README 检查。** 实测中一次调查因判断「元数据信号 0 命中，无触发必要」而整体跳过了 README 检查，实际上有 4 个候选的描述含 `example`（`Minimal live-editing example for React`、`Examples for "Idiomatic Redux"` 等）——漏检直接导致最终 Top 5 与另一次调查不一致。**命中与否是查出来的，不是看出来的。**

**预算约束**：命名、来源两类信号纯元数据判断，对全部仓库执行。README 与结构信号需要额外读取，**只对粗排前 15 个候选执行**——对上百个仓库逐个抓 README 会使调用量翻倍。未做 README 检查的仓库仅按元数据信号判定，并在数据说明中注明覆盖范围。

**克制原则**：信号不足就不要判定。误判会把真正的代表作降到看不见，代价远高于漏判。特别注意：名字里有 `demo` 的正式项目、以 `learn-` 开头的自研学习工具，都不应仅凭命名判定。

### 1.3 fork 的实质改动判断

fork 仓库需要区分两种情况：

| 情况 | 判定依据 |
|---|---|
| 无实质自有 commit | 本人 commit 数 < 10，或仅有同步上游的合并提交 |
| 有显著自有改动 | 本人 commit ≥30，或存在上游没有的独立功能/模块 |

后者说明是真实的开源参与，降权应当从轻。

## 二、评分模型

总分 100 分，四个维度加权：

| 维度 | 权重 | 说明 |
|---|---|---|
| 技术价值 | 35 | 项目本身的工程含量 |
| 活跃程度 | 25 | 是否持续投入 |
| 个人贡献 | 25 | 是否本人主导 |
| 项目影响力 | 15 | 外部认可度 |

### 关于权重的取舍

影响力（stars）只占 15 分，是刻意压低的。

本 Skill 的主要调查对象是普通开发者与学生，这类用户绝大多数仓库 stars 为 0。若按业界常见做法把 stars 设为主导权重，所有候选项目会一起归零，排序完全失效。**技术价值与个人贡献才是这个场景下真正有区分度的信号。**

若将来需要调查知名开源作者，可以考虑提高影响力权重，但那属于不同的使用场景，应作为参数而非改动默认值。

---

### 2.1 技术价值（35 分）

| 信号 | 判定 | 得分 |
|---|---|---|
| **代码规模** | 空仓库 / 仅 README | 0 |
| | < 500 行 | 3 |
| | 500 ～ 3,000 行 | 8 |
| | 3,000 ～ 15,000 行 | 12 |
| | > 15,000 行 | 15 |
| **架构复杂度** | 单文件脚本 | 0 |
| | 简单多文件，无分层 | 4 |
| | 有模块划分或分层设计 | 8 |
| | 多模块 + 测试 + CI | 12 |
| **技术栈难度** | 常见脚手架默认栈 | 0 |
| | 主流框架的常规应用 | 3 |
| | 需要专门领域知识 | 8 |

**「需要专门领域知识」的判定**：编译器/解释器、分布式系统、数据库内核、操作系统/内核、模型训练与推理优化、图形渲染、密码学、嵌入式/驱动、协议实现等。仅仅调用某个 AI API 不算——那是主流框架的常规应用。

**代码规模必须按各语言的源码字节数总和折算**，约 30 字节 ≈ 1 行。这个数据在 Step 5a 一次调用即可取得。

**不要用仓库体积（disk usage）估算代码规模。** 仓库体积包含图片、构建产物与 git 历史，误差可达三个数量级——实测某博客仓库体积 206,340 KB 而实际源码仅 49 KB，偏差 4,200 倍；某单 commit 仓库体积 10,230 KB 而源码仅 24 KB。用它分档会让资源密集型仓库拿满分并挤掉真正的代表作。仓库体积**只能**用于判断「是否几乎为空」（≤2 KB）。

**代码规模在 Step 4 即可计算**（语言字节数随批量枚举返回，无额外成本）。**架构复杂度与技术栈难度**需要目录结构与依赖清单，只在 Step 5b 对最终 Top N 计算。详见第六节。

---

### 2.2 活跃程度（25 分）

| 信号 | 判定 | 得分 |
|---|---|---|
| **最近 push 距今** | < 1 个月 | 10 |
| | 1 ～ 3 个月 | 8 |
| | 3 ～ 6 个月 | 5 |
| | 6 ～ 12 个月 | 2 |
| | > 12 个月 | 0 |
| **commit 时间跨度** | < 1 周 | 0 |
| | 1 周 ～ 1 个月 | 3 |
| | 1 ～ 6 个月 | 6 |
| | > 6 个月 | 9 |
| **commit 总数** | < 10 | 0 |
| | 10 ～ 49 | 3 |
| | 50 ～ 199 | 5 |
| | ≥ 200 | 6 |

「commit 时间跨度」指**首次与最近一次 commit 的时间差**。这个信号用于区分**一次性突击**与**持续建设**——两个都有 80 次 commit 的项目，跨度 3 天和跨度 1 年含义完全不同。

**禁止用仓库创建时间到最近 push 时间代替 commit 跨度。** 二者不等价：实测某仓库只有 1 个 commit（真实跨度 0 天，应得 0 分），但创建到 push 相隔 258 天，代理算法给了满分 9 分，把一次性代码倾倒判成了持续建设。拿不到真实 commit 数据时，这一项计 0 分，并记入数据缺口——**宁可少给分，不要用错误的代理**。

---

### 2.3 个人贡献（25 分）

| 信号 | 判定 | 得分 |
|---|---|---|
| **本人 commit 占比** | < 20% | 0 |
| | 20% ～ 50% | 5 |
| | 50% ～ 80% | 9 |
| | > 80% | 12 |
| **是否 owner 且非 fork** | 是 | 8 |
| | 否 | 0 |
| **是否持续维护** | commit 分布跨越 ≥3 个不同月份 | 5 |
| | 否 | 0 |

占比无法核实时（commit 作者信息不公开等），按 owner 身份保守估算，并在报告的「数据说明」中标注为估算值。

---

### 2.4 项目影响力（15 分）

| Stars | 得分 |
|---|---|
| 0 | 0 |
| 1 ～ 9 | 3 |
| 10 ～ 49 | 7 |
| 50 ～ 199 | 11 |
| ≥ 200 | 15 |

Forks 与 Watchers 作为佐证不单独计分。

**饱和是预期行为**：知名开发者可能有几十个仓库 stars ≥200，全部拿满 15 分，这个维度在其身上不产生区分度——此时排序由其余 85 分决定，这正是压低影响力权重的目的。不要为了制造区分度而细分高分段，那会让 stars 重新主导排序。

**异常信号**：若 forks 明显高于 stars，通常是课程作业或教程模板的特征（学生 fork 作业仓库但不 star），应回到 1.2 触发教程识别检查。

## 三、降权系数

对总分做乘法调整。多个条件同时命中时，**取最低系数**，不叠乘。

| 条件 | 系数 |
|---|---|
| fork 且无实质自有 commit | ×0.1 |
| fork 但有显著自有改动 | ×0.6 |
| 命中教程 / 模板判定 | ×0.3 |
| 空仓库或仅有 README | ×0.1 |
| 已 archived | ×0.8 |

archived 的 ×0.8 是轻度降权：归档说明项目已停止维护，但不否定其技术价值——一个完成度高的归档项目仍可能是代表作。

---

## 四、时间窗口定义

统一口径，避免各处理解不一：

| 术语 | 定义 |
|---|---|
| 最近活跃 | 最近一次 push 在 90 天内 |
| 长期维护 | commit 分布跨越 ≥3 个不同月份 |
| 近期方向 | 最近 12 个月内有 commit 的仓库集合 |
| 技术成长轨迹 | 按仓库创建年份分组统计 |

## 五、复杂度星级对照

用于报告中呈现单个项目的复杂度：

| 综合得分 | 星级 |
|---|---|
| 0 ～ 19 | ★☆☆☆☆ |
| 20 ～ 39 | ★★☆☆☆ |
| 40 ～ 59 | ★★★☆☆ |
| 60 ～ 79 | ★★★★☆ |
| 80 ～ 100 | ★★★★★ |

星级反映的是**项目的工程复杂度**，不是对开发者能力的评级。

## 六、分阶段评分

评分模型需要的数据分三个档次的获取成本，因此排序分三阶段进行。**任何一个阶段都不得用估算代理去补当阶段拿不到的信号**——宁可让该项计 0 分。

| 阶段 | 每仓库调用 | 可用数据 | 可计算 | 分制 | 产出 |
|---|---|---|---|---|---|
| **Step 4 粗筛** | 0 | 仓库元数据 + **每仓库语言字节数** | 影响力 15 + 最近 push 10 + owner 身份 8 + 代码规模 15 | 48 分制 | Top 15 候选，**不是最终排名** |
| **Step 5a 主排序** | 1 | + 贡献者列表 | 追加 commit 数 6 + 本人占比 12 | 66 分制 | 最终 Top N |
| **Step 5b 深度分析** | 5 | + commit 首末时间、目录结构、依赖、README | 追加 跨度 9 + 持续维护 5 + 架构复杂度 12 + 技术栈难度 8 | 100 分制 | Top N 内部顺序、复杂度星级、报告内容 |

**代码规模必须在 Step 4 就参与计算。** 各仓库的语言字节数在 Step 2 的批量枚举里一并返回，**不需要任何额外调用**——曾误以为它需要逐仓库获取而放到了 Step 5a，这个前提是错的。

放在 Step 4 是必须的，不是优化。实测某用户在 33 分制下出现 **17 个仓库精确并列 23.0 分**：stars ≥200 的老仓库全部是「影响力 15 + push 0 + owner 8」，粗筛截断线正落在这个同分区里。最终排名第 1 的项目当时卡在候选名单**最后一格**，与被淘汰者只差 8 颗 star——粗筛几乎丢掉了冠军。加入代码规模后同一用户的粗筛变成 48 分制，该项目升至第 4，Top 11 分层清晰。

**为什么候选数是 15。** 即使加入代码规模，截断线附近仍可能落在同分区。`max(15, top_n × 3)` 留出余量，而 Step 5a 每仓库只需 1 次调用，扩大候选的边际成本很低。

**commit 跨度为什么仍放在 5b。** 取跨度需额外两次调用。实测表明加入跨度会改变 Top 5 的内部顺序，但选出的仍是同一批项目——它对「选谁」没有决定作用，对「谁排前面」才有。


### 为什么粗筛不能直接砍到 top_n

Step 4 拿不到 commit 与内容层面的信号，**在残缺分制上做最终淘汰会退化成大面积并列**，此时截断等同随机选择，直接破坏第七节的一致性要求。

更严重的是**淘汰不可逆**：Step 5 的修正只能调整已入选者的顺序，救不回没入选的项目。实测中最终排名第 1 的项目曾卡在候选名单最后一格，与被淘汰者只差 8 颗 star——粗筛几乎丢掉了冠军。

因此 Step 4 的职责是**粗筛而非排名**：把明显不可能入选的排除掉，剩下的交给 Step 5a 用充分数据决定。

### 残留限制

Step 5b 的 34 分只对最终 Top N 计算，因此第 N+1 名理论上仍可能反超。这是刻意接受的代价：那些信号需要逐仓库读取目录树、依赖与 commit 历史，对全部候选做会使调用量翻倍。

缓解在于这些信号与前两阶段已算准的信号高度相关——架构复杂度与代码规模相关，持续维护与 commit 数相关。两次独立实测中 5b 都只调整了 Top 5 的内部顺序，没有换人。**但报告中不得声称排序绝对精确。**

## 七、一致性要求

同一用户在短期内两次调查，Top 3 项目集合应当一致。若出现不一致，通常来自：

- **同分并列**——这是排序不稳定的首要来源。出现并列时按 stars 降序、再按仓库名字典序破平，**不得依赖数据返回的偶然顺序**
- 估算环节引入了随意性——代码规模、架构复杂度的判定应严格对照上表，不凭印象给分
- 教程识别的信号计数不稳定——命中条数必须逐条核对，不要凭整体感觉判定
- 用了被禁止的代理指标（仓库体积代替代码规模、创建时间代替 commit 跨度）
- 深度分析修正得分时脱离了评分表

出现排序不稳定时，按此顺序检查。
