# GitHub Scout — 调查方法论

本文件是 GitHub Scout 的核心方法论，**平台无关**。

它只描述「每一步需要什么信息、产出什么结论」，不涉及任何具体工具、命令或 API 的名称。怎么拿到这些信息，由各平台的 adapter 决定。

配套文件：

- `repo-ranking.md` — 仓库过滤与评分规则
- `report-format.md` — 报告输出格式

---

## 总体流程

调查分两个阶段：

```
阶段 1：Profile Scout        阶段 2：Repository Analyzer
──────────────────────      ─────────────────────────────
用户 → 仓库全集 → 候选 12    Top N 主排序 → 逐个深入 → 画像
       (广度优先)                   (深度优先)
```

阶段 1 用低成本的元数据覆盖全部仓库，阶段 2 只对少数入选项目付出高成本。**不要在阶段 1 就深入读取仓库内容**——这是调用预算失控的主要原因。

---

## Step 1：用户解析

**输入**：GitHub 用户名，或用户主页 URL（需从中提取用户名）。

**需要获取的信息**：

- 用户是否存在，账号类型（个人 / 组织）
- 显示名、简介、所在地、个人站点
- 账号创建时间
- 公开仓库数、followers / following 数

**判断逻辑**：

- 用户不存在 → 立即终止，说明未找到该用户，不要猜测相近用户名
- 账号类型为组织 → 提示调查对象是组织而非个人，询问是否继续（组织的「个人贡献」维度不适用）
- 简介和个人站点是技术方向的重要线索，但**只作参考不作结论**——最终方向判断以仓库实际内容为准

**产出**：用户基本档案，供报告「基本信息」一节使用。

**降级处理**：profile 信息部分缺失（无简介、无站点）不影响后续流程，正常继续。

---

## Step 2：仓库枚举

**输入**：已确认存在的用户名。

**需要获取的信息**（对每个公开仓库）：

- 仓库名与描述
- 主语言
- stars / forks / watchers 数
- 创建时间、最近 push 时间
- 是否为 fork；若是，其上游仓库
- 是否 archived
- 是否由 template 生成
- 仓库体积（**仅用于判断是否几乎为空，不得用于估算代码规模**）

**判断逻辑**：

- 一次性取回全部公开仓库，不要分批猜测
- 仓库数超过 100 时，先按「最近 push 时间」和「stars」粗筛出前 50 个候选，再进入 Step 3，以控制调用预算
- 此步骤**只看元数据**，不读取任何仓库内容
- **枚举失败要重试**：大账号的批量查询可能超时（实测 299 仓库的账号出现过一次网关超时，重试即通过）。失败后重试一次；仍失败则减半单次请求量分批取回。**枚举失败不能降级为「跳过」**——后续所有步骤都依赖这份全集

**产出**：仓库全集及其元数据表。同时可统计出语言分布，供报告「技术方向」一节使用。

**降级处理**：

- 公开仓库数为 0 → 跳至 Step 6 的空结果分支
- 元数据不完整（如体积缺失）→ 记入数据缺口，评分时该项按最保守值处理

---

## Step 3：仓库过滤

**输入**：Step 2 的仓库全集。

**判断逻辑**：应用 `repo-ranking.md` 的过滤规则，将仓库分为三类：

| 类别 | 处理 |
|---|---|
| 原创且有实质内容 | 进入评分 |
| fork / 教程 / 模板 / 空仓库 | 进入评分，但应用降权系数 |
| 完全为空且无任何活动 | 记录数量，不参与排序 |

关键原则：**降权而非排除**。被降权的仓库仍然参与排序，因为当一个用户的仓库全部是 fork 时，报告仍需给出有依据的结论（见 FR-7），而不是「没有可分析的项目」。

教程/模板的识别信号见 `repo-ranking.md`。识别时保持克制：命中信号不足就不要判定，误判会把真正的代表作降权到看不见。

**产出**：带分类标记的候选仓库集。

---

## Step 4：代表项目排序

**输入**：Step 3 的候选仓库集。

**这一步是粗筛，不是排名。** 它的唯一职责是把明显不可能入选的仓库排除掉，剩下的交给 Step 5a 用充分数据决定。

**判断逻辑**：只用元数据可算的三项信号打分——影响力、最近 push 时间、owner 身份，合计 33 分（见 `repo-ranking.md` 第六节）。应用降权系数后降序排列。

**严禁用代理指标补足缺失的信号。** 仓库体积不等于代码规模，创建时间不等于 commit 跨度。拿不到的信号一律计 0 分，不要猜——用错误的代理比少给分危害大得多。

**产出**：前 `max(12, top_n × 2)` 个候选进入 Step 5a。**不要在这一步就砍到 top_n**：33 分制上会出现大面积同分，此时做淘汰等同随机选择，而且淘汰不可逆——Step 5 的修正只能调整已入选者的顺序，救不回没入选的项目。

**降级处理**：候选不足时，有多少带多少，并在报告中说明。

---

## Step 5a：主排序

**输入**：Step 4 的 12 个候选。**决定最终 Top N 的是这一步，不是 Step 4。**

对每个候选，**需要获取的信息**（每个仓库两项，成本可控）：

- **各语言的源码字节数**——用于计算真实代码规模
- **贡献者列表及各自 commit 数**——用于计算 commit 总数与本人占比

**判断逻辑**：

1. **代码规模**：语言字节数总和折算行数（约 30 字节 ≈ 1 行）。**不要用仓库体积**。
2. **commit 总数**：贡献者 commit 数求和即可，是近似值但足够分档。
3. **本人占比**：本人 commit 数 ÷ 总数。
4. 按 `repo-ranking.md` 的 66 分制打分，应用降权系数，降序排列。
5. 同分时按 stars 降序、再按仓库名字典序破平，**不得依赖数据返回的偶然顺序**。

**产出**：最终 Top N（默认 5）及其 66 分制得分。

**降级处理**：贡献者信息不可得 → 占比与 commit 数计 0 分，记入数据缺口，不要估算。

---

## Step 5b：深度分析

**输入**：Step 5a 选出的 Top N。

对每个仓库，**需要获取的信息**：

- README 内容——判断项目意图的首要依据
- 目录结构——判断架构组织方式
- 依赖清单——判断技术栈
- 首末 commit 时间——计算真实的 commit 跨度

**判断逻辑**：

1. **项目目的**：优先看 README 的开篇说明。README 缺失或过于简略时，从目录结构与依赖反推，并标注该判断为推测。
2. **技术栈**：以依赖清单为准，README 中的技术声明作为佐证。两者矛盾时以依赖清单为准——README 常年久失修。
3. **架构复杂度**：看模块划分、是否有测试目录、是否有 CI 配置，而非看代码行数。
4. **commit 跨度**：取首末 commit 的时间差。**不要用仓库创建时间到最近 push 的间隔代替**——单 commit 仓库会因此被误判成长期维护。
5. **补齐得分**：加上跨度、持续维护、架构复杂度、技术栈难度四项，得到 100 分制总分，用于复杂度星级。

这一步可以调整 Top N 内部的顺序，但**不改变入选名单**——名单在 Step 5a 已用充分数据定下。实测中含跨度与不含跨度的两种排序选出的是同一批项目，只是先后不同。

**判断纪律**：

- 每条结论都要能指向具体依据（某个文件、某段 README、某个时间区间）
- 区分「观察到的事实」与「据此的推测」，报告中不要把推测写成事实
- 不做代码质量评判——不评价代码写得好不好，只描述项目的结构与规模

**产出**：每个项目的分析卡片，含目的、技术栈、复杂度评级、个人贡献。

**降级处理**：

- 仓库无法访问（已删除、转为私有）→ 跳过，从 Step 5a 的候选列表补入下一个
- 无 README → 从结构推断，标注为推测

---

## Step 6：画像生成

**输入**：Step 1 的用户档案、Step 2 的语言分布、Step 5b 的项目分析卡片。

**综合判断**：

1. **主要语言**：按仓库数量与代码规模加权，而非仅按仓库数——一个大型 Rust 项目比十个小 Python 脚本更能说明方向。
2. **主要领域**：从 Top N 项目的目的与技术栈中归纳。领域判断需要至少两个项目佐证，单个项目不足以确立方向。
3. **活跃度**：基于最近 12 个月的 commit 分布，而非单一的最近 push 时间。
4. **技术特征**：描述可观察的特征（偏工程实现 / 偏算法实验 / 偏工具建设 / 多为学习实践），**不评价水平高低**。

**产出**：按 `report-format.md` 组织的完整报告。

### 空结果与边界分支

| 情况 | 应输出的结论 |
|---|---|
| 公开仓库数为 0 | 说明该用户无公开仓库，无法形成技术画像；如 profile 有简介或站点，可提示这些是仅有的公开线索 |
| 全部为 fork | 说明其公开活动以参与他人项目为主；分析 fork 中是否有实质自有改动，有则作为贡献证据 |
| 全部为教程/模板 | 说明其公开仓库以学习实践为主；据此描述学习方向与时间线，不引申为能力判断 |
| 仓库存在但全部为空 | 说明账号已注册仓库但无实质内容 |

这些分支**必须产出报告**，不允许以「无可分析内容」草草结束。

---

## 贯穿全流程的原则

1. **广度在前，深度在后**——元数据能判断的，不要读取内容。
2. **降权优于排除**——保留所有仓库参与排序，避免过滤掉唯一的信息来源。
3. **结论可回溯**——每条判断都能指向具体依据。
4. **区分事实与推测**——推测必须标注。
5. **缺口显式声明**——无法核实的数据写进报告的「数据说明」，不静默略过。
6. **描述而非评判**——输出技术画像，不输出对人的价值判断。
