# GitHub Scout — 仓库过滤与评分规则

本文件定义仓库的过滤规则与评分模型，**平台无关**。

这是保证跨平台结论一致的关键文件：任何 adapter 对同一个用户的 Top N 排序与复杂度评级都应当由本文件唯一决定。**规则有歧义时，在这里修正，不要在 adapter 里打补丁。**

配套文件：`methodology.md`（流程）、`report-format.md`（输出）。

---

## 一、过滤规则

### 1.1 分类

| 类别 | 判定 | 处理 |
|---|---|---|
| 原创项目 | 非 fork，有实质内容 | 正常评分 |
| fork 项目 | 标记为 fork | 评分后应用降权系数 |
| 教程 / 模板 | 命中 1.2 的信号 ≥2 条 | 评分后应用降权系数 |
| 空仓库 | 无内容或仅有 README/LICENSE | 评分后应用降权系数 |

**降权而非排除。** 所有仓库都参与排序。当一个用户的仓库全是 fork 或全是教程项目时，报告仍需给出有依据的结论。

### 1.2 教程 / 模板项目识别

命中 **≥2 条**即判定：

- **命名信号**：仓库名或描述含 `tutorial`、`learn`、`learning`、`practice`、`demo`、`test`、`example`、`hello`、`homework`、`assignment`、`course`、`bootcamp`、`训练营`、`课程设计`、`大作业`
- **README 信号**：README 明显是课程模板或脚手架自带，未做实质修改；或内容为教程步骤而非项目说明
- **commit 信号**：commit 全部集中在 1～3 天内，且 message 多为 `update`、`commit`、`init`、`fix`、`.` 等无信息量内容
- **结构信号**：目录结构与知名脚手架或教程仓库完全一致，无自有扩展
- **来源信号**：仓库由 template 生成，且生成后改动很少

**克制原则**：信号不足就不要判定。误判会把真正的代表作降到看不见，代价远高于漏判。特别注意：名字里有 `demo` 的正式项目、以 `learn-` 开头的自研学习工具，都不应仅凭命名判定。

### 1.3 fork 的实质改动判断

fork 仓库需要区分两种情况：

| 情况 | 判定依据 |
|---|---|
| 无实质自有 commit | 本人 commit 数 < 10，或仅有同步上游的合并提交 |
| 有显著自有改动 | 本人 commit ≥30，或存在上游没有的独立功能/模块 |

后者说明是真实的开源参与，降权应当从轻。

## 二、评分模型

总分 100 分，四个维度加权：

| 维度 | 权重 | 说明 |
|---|---|---|
| 技术价值 | 35 | 项目本身的工程含量 |
| 活跃程度 | 25 | 是否持续投入 |
| 个人贡献 | 25 | 是否本人主导 |
| 项目影响力 | 15 | 外部认可度 |

### 关于权重的取舍

影响力（stars）只占 15 分，是刻意压低的。

本 Skill 的主要调查对象是普通开发者与学生，这类用户绝大多数仓库 stars 为 0。若按业界常见做法把 stars 设为主导权重，所有候选项目会一起归零，排序完全失效。**技术价值与个人贡献才是这个场景下真正有区分度的信号。**

若将来需要调查知名开源作者，可以考虑提高影响力权重，但那属于不同的使用场景，应作为参数而非改动默认值。

---

### 2.1 技术价值（35 分）

| 信号 | 判定 | 得分 |
|---|---|---|
| **代码规模** | 空仓库 / 仅 README | 0 |
| | < 500 行 | 3 |
| | 500 ～ 3,000 行 | 8 |
| | 3,000 ～ 15,000 行 | 12 |
| | > 15,000 行 | 15 |
| **架构复杂度** | 单文件脚本 | 0 |
| | 简单多文件，无分层 | 4 |
| | 有模块划分或分层设计 | 8 |
| | 多模块 + 测试 + CI | 12 |
| **技术栈难度** | 常见脚手架默认栈 | 0 |
| | 主流框架的常规应用 | 3 |
| | 需要专门领域知识 | 8 |

**「需要专门领域知识」的判定**：编译器/解释器、分布式系统、数据库内核、操作系统/内核、模型训练与推理优化、图形渲染、密码学、嵌入式/驱动、协议实现等。仅仅调用某个 AI API 不算——那是主流框架的常规应用。

**估算与修正**：流程 Step 4 阶段只有元数据，代码规模按仓库体积估算（粗略对应：< 100 KB ≈ 小型，100 KB ～ 1 MB ≈ 中型，> 1 MB ≈ 大型，注意排除仓库内的大体积资源文件）。进入 Step 5 深度分析后，用实际观察修正。

---

### 2.2 活跃程度（25 分）

| 信号 | 判定 | 得分 |
|---|---|---|
| **最近 push 距今** | < 1 个月 | 10 |
| | 1 ～ 3 个月 | 8 |
| | 3 ～ 6 个月 | 5 |
| | 6 ～ 12 个月 | 2 |
| | > 12 个月 | 0 |
| **commit 时间跨度** | < 1 周 | 0 |
| | 1 周 ～ 1 个月 | 3 |
| | 1 ～ 6 个月 | 6 |
| | > 6 个月 | 9 |
| **commit 总数** | < 10 | 0 |
| | 10 ～ 49 | 3 |
| | 50 ～ 199 | 5 |
| | ≥ 200 | 6 |

「commit 时间跨度」指首次与最近一次 commit 的时间差。这个信号用于区分**一次性突击**与**持续建设**——两个都有 80 次 commit 的项目，跨度 3 天和跨度 1 年含义完全不同。

---

### 2.3 个人贡献（25 分）

| 信号 | 判定 | 得分 |
|---|---|---|
| **本人 commit 占比** | < 20% | 0 |
| | 20% ～ 50% | 5 |
| | 50% ～ 80% | 9 |
| | > 80% | 12 |
| **是否 owner 且非 fork** | 是 | 8 |
| | 否 | 0 |
| **是否持续维护** | commit 分布跨越 ≥3 个不同月份 | 5 |
| | 否 | 0 |

占比无法核实时（commit 作者信息不公开等），按 owner 身份保守估算，并在报告的「数据说明」中标注为估算值。

---

### 2.4 项目影响力（15 分）

| Stars | 得分 |
|---|---|
| 0 | 0 |
| 1 ～ 9 | 3 |
| 10 ～ 49 | 7 |
| 50 ～ 199 | 11 |
| ≥ 200 | 15 |

Forks 与 Watchers 作为佐证不单独计分。

**异常信号**：若 forks 明显高于 stars，通常是课程作业或教程模板的特征（学生 fork 作业仓库但不 star），应回到 1.2 触发教程识别检查。

## 三、降权系数

对总分做乘法调整。多个条件同时命中时，**取最低系数**，不叠乘。

| 条件 | 系数 |
|---|---|
| fork 且无实质自有 commit | ×0.1 |
| fork 但有显著自有改动 | ×0.6 |
| 命中教程 / 模板判定 | ×0.3 |
| 空仓库或仅有 README | ×0.1 |
| 已 archived | ×0.8 |

archived 的 ×0.8 是轻度降权：归档说明项目已停止维护，但不否定其技术价值——一个完成度高的归档项目仍可能是代表作。

---

## 四、时间窗口定义

统一口径，避免各处理解不一：

| 术语 | 定义 |
|---|---|
| 最近活跃 | 最近一次 push 在 90 天内 |
| 长期维护 | commit 分布跨越 ≥3 个不同月份 |
| 近期方向 | 最近 12 个月内有 commit 的仓库集合 |
| 技术成长轨迹 | 按仓库创建年份分组统计 |

## 五、复杂度星级对照

用于报告中呈现单个项目的复杂度：

| 综合得分 | 星级 |
|---|---|
| 0 ～ 19 | ★☆☆☆☆ |
| 20 ～ 39 | ★★☆☆☆ |
| 40 ～ 59 | ★★★☆☆ |
| 60 ～ 79 | ★★★★☆ |
| 80 ～ 100 | ★★★★★ |

星级反映的是**项目的工程复杂度**，不是对开发者能力的评级。

---

## 六、一致性要求

同一用户在短期内两次调查，Top 3 项目集合应当一致。若出现不一致，通常来自：

- 估算环节引入了随意性——代码规模、架构复杂度的判定应严格对照上表，不凭印象给分
- 教程识别的信号计数不稳定——命中条数必须逐条核对，不要凭整体感觉判定
- 深度分析修正得分时脱离了评分表

出现排序不稳定时，检查这三处。
